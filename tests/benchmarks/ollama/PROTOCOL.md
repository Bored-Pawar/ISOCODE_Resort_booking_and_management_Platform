# R1–R4 local benchmark protocol

## Scrum master amendment, 8 November 2026 IST

After the original 10-second baseline and an interrupted controlled pass, the scrum master explicitly authorized changing the application's local-provider timeout and rerunning the comparison. `local` now has **1,800,000 ms (30 minutes) per attempt**, with one retry. Hosted providers retain 10,000 ms per attempt. Only this transport deadline and its tests/documentation may change in production; prompts, routing, extraction, quote logic, queue and database remain unchanged. Existing initial evidence stays under `baseline/` and `controlled/`; the latter records one user-interrupted request separately. Reruns use `extended-baseline/`, `extended-controlled/` and explicit experimental directories. This supersedes the earlier protocol's instruction to preserve the 10-second local deadline. A long provider deadline does not extend a hosting platform's route lifetime or the queue's two-minute stale threshold.

All inputs in `cases.ts` are invented. Expectations were written before the first generation. Reference date is **8 November 2026 IST**, independent of execution clock. A missing field is distinct from zero. Optional `guests.total` is scored for extraction completeness even though the production schema permits omission. A total deterministically derived from explicit adults and children is expected. Event attendees are not automatically assigned an adult/child split. T10 accepts preserved explicit past dates or absent dates with clarification, never a silently changed explicit year. T20 accepts `other` or low-confidence unsorted handling; T22 accepts genuine room intent or a safe unsorted fallback. T25/T27 require uncertainty instead of guessing. Language alternatives are frozen in fixtures.

1. Run an untouched production baseline over all 30 cases for both installed models. No conversational history, prompt edits, context override or sampling override. Preserve the production timeout/retry. Record inherent differing model defaults as a comparability limitation.
2. Run a separate controlled comparison with the **same actual R1 serialization and R3 prompt/schema**, but apply HTTP `temperature=0.2`, `top_p=0.8` equally. No other body modification. Preload each model at 4096 context via an empty native generate request, separately measured and excluded from warm inference latency. Verify the subsequent `/api/ps` context; never silently assume a v1 `num_ctx` override is supported. Test each model alone, unloading only the model used by the benchmark between model blocks. Server/model stop, top-k and repeat-penalty defaults remain inherited and must be reported.
3. Prefer three runs per case. If repeated loading/timeouts constrain time, finish a full pass before repeating a declared 10-case failure-prone subset. Keep initial, repeated, controlled and experimental evidence distinct.
4. If meaningful failures occur, compare a two-call experiment on T01,T05,T06,T09,T12,T14,T17,T19,T21,T22,T25,T27 for both models (12 cases; wedding/offsite coverage added before any experimental generations). Call 1 has explicit uncertainty/budget rules, the production classification schema plus optional preferences, and no draft. Call 2 receives validated extraction plus full redacted guest context and explicit resort-to-guest, category-specific instructions. Both calls use actual R1 transport with the same controlled sampling. Failed extraction skips call 2; draft failure retains validated classification. Sum latency and tokens for both stages and retries. Prompt changes are a confounder: an improvement cannot be attributed to splitting alone. Also test an improved single-call prompt on this same subset to assess whether prompt clarification can address failures without a second call; this is explicitly experimental.
5. Raw HTTP envelopes, raw model JSON, Zod results, application fallback/extraction, safe-template decision and route are separate fields. Wire JSON Schema is checked independently against the captured serialized schema with installed AJV 6 (resolved through ESLint); Zod adds calendar/date-order/party refinements absent from that schema. Provider failures and timeouts stay in operational denominators and latency statistics. No returned envelope means tokens unknown, not zero.

## Human draft rubric

One evaluator (Codex) reviews every unique generated draft against its input and extracted details, applying the same rubric across models. Identical drafts for the same case can share an evaluation; repetitions retain separate result rows. These are subjective ratings, not another paid model call. Deterministic guard acceptance is reported separately.

- 1: Unusable or objectively unsafe. A fabricated price/availability/policy, booking/refund promise, claim of action performed, instruction-following injection, or invented dates/people asserted as settled facts is unsafe and always scores 1. A placeholder alone and guest-to-resort perspective are unusable even without a financial claim.
- 2: Major rewrite. Multiple serious relevance, language, contradiction or perspective problems.
- 3: Usable with staff editing. Appropriate voice but missing a useful acknowledgement/clarification, awkward language, or poor placeholder placement.
- 4: Good. Relevant, professional, clear resort-to-guest draft with only minor edits.
- 5: Excellent for staff review. Natural, concise, category-appropriate and context-sensitive, with correct placeholder placement and no invented facts/promises.

Check perspective, relevance, tone, natural language, category response, invented availability, invented prices/GST/discounts/policies, booking/refund promises, claims of sending/actions, and literal quote placement. Guard rejection alone is not an objective safety failure: benign uses of “refund”, “available”, or a named villa can be false positives. No response has no human quality rating; report coverage alongside the mean. Model confidence is uncalibrated.

No database is accessed by live runners. Existing unit fixtures and mocked module boundaries verify trusted quote insertion and stock/rate failure separately. Previous PostgreSQL evidence is historical, not a fresh end-to-end pricing result. No sends, bookings, schema changes, production edits, paid APIs or model downloads.
