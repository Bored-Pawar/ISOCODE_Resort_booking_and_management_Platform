## S1 Codex B5 (local implementation; independent review pending)
- **What:** payment validation uses only saved `total_paise`. The transaction first checks an existing provider ID, lazily expires only its target booking, and conditionally transitions HELD to CONFIRMED or settles an expiry crossed since that initial check. It writes the payment, stock movement, event and promo-use increment atomically. Existing terminal states are preserved; distinct extra charges are recorded for refund.
- **Idempotency:** `INSERT ... ON CONFLICT DO NOTHING` arbitrates the unique provider ID without treating unrelated constraint failures as duplicates. Same-booking/provider/amount retries return the saved success (`ALREADY_CONFIRMED`) or refund result; conflicting reuse returns `INVALID_INPUT` after rolling back any tentative transition. Late-payment retries create one refund obligation and audit note per provider ID.
- **Clock and lock order:** take the booking write lock before payment/stock locks. The conditional update uses one database decision clock; because its expression can be evaluated before waiting on a row lock, a post-lock database-clock check rejects a now-stale confirmation by rollback and one expiry retry. A separate internal clock-expression dependency enables exact SQL equality tests without a public clock parameter. PostgreSQL deadlock/serialization failures also get one transaction retry; exhausted infrastructure failures are thrown after rollback.

## S1 enquiry intake (Claude Code)

### Q1 Ingest and list
- **What:** `enquiries.ingest()` validates with the frozen Zod schema, saves one `enquiries` row (`ai_status='pending'`, `lane='unsorted'`) and returns `ENQ-XXXXX`. `list()` reads newest first, joins the owner's role, takes `summary` from `extracted`. Additive: `ingestFrom(input, { source?, consentVersion? })` and `list({ limit })`; the C1 signatures still work unchanged.
- **Why:** ids are generated in app code (`crypto.randomInt`, alphabet without 0/O/1/I) and the insert retries on a primary key conflict, so there is no sequence to migrate. With a `source`, a transaction takes `pg_advisory_xact_lock` on the provider message id, looks for it in `extracted.source` and returns the existing row, so concurrent retries cannot double insert. Verified: 5 parallel posts of one message id gave one row.
- **Tradeoffs:** the schema has no external-id column or unique index, so the dedupe is a lock plus a sequential scan over a small table; a unique index on `extracted->'source'` would be the proper fix (needs the DB owner). `extracted.source` must survive R3 (see `04`).

### Q3 Inbound webhooks
- **What:** pure mappers in `modules/enquiries/inbound.ts` (Postmark: `From`, `FromName`, `Subject`, `TextBody`, `MessageID`; Meta Cloud API: `entry[].changes[].value.messages[]` with `contacts[]` for the profile name) and one shared handler. Secret header, 256 KB cap, Zod, then ingest. Responses: 401 bad secret, 400 malformed, 200 `{ enquiryIds, duplicates, skipped }`. Status-only and non-text WhatsApp events are 200 and skipped. A failed ingest returns 500 so the provider retries; safe because ingest is idempotent.
- **Why:** providers retry on non-2xx, so only genuinely retryable failures return 5xx. No AI is called here (R1/R2), and logs carry the error name only.
- **Tradeoffs:** no Meta `X-Hub-Signature-256` check or GET verification handshake; the shared secret header stands in for both until a real provider is connected. `export const runtime` is rejected by `cacheComponents`, so the handlers rely on the Node default.

## S2 multi-room B10 (Claude Code, overnight 2026-11-08)

### Pricing and hash
- **What:** `QuoteInput.rooms` (1 to 4 lines) priced in one SQL statement (VALUES list of lines joined to rooms, plans and rates, plus slabs and promo). Cells are (line, night). A flat promo is allocated once over every cell flattened in (line_no, date) order with the R09 algorithm; GST slab per cell after its discount. Line totals sum cells, order totals sum lines.
- **Why:** choosing a slab on a per-date sum across rooms would push two Rs 4,000 rooms into 18%; tested at unit and database level. The hash keeps line order so the price a guest saw is tied to that exact cart; occupancy stays out of it.
- **Tradeoffs:** `MissingTaxSlab` still returns `NO_RATE` without a `lineIndex` (a missing schedule is not a line fault). Line checks stop at the first failing line.

### Locking, expiry, confirm
- **What:** `lockNights` locks every `(room_type_id, date)` row of the cart in one statement `ORDER BY room_type_id, date FOR UPDATE`; demand is merged per type in JS (count only), never the lock order. `adjustNights` sums deltas per (type, date), takes one ordered lock and one `UPDATE ... FROM (VALUES ...)`. Expiry prelocks the union of released and requested rows in one ordered statement, then releases per type from `booking_rooms`; confirm does the same with `sold`.
- **Why:** any two carts lock in the same global order, so `[T1, T2]` vs `[T2, T1]` serialises instead of deadlocking (new test 1 checks `pg_stat_database.deadlocks`).
- **Tradeoffs:** the lazy expiry sweep is still one statement (minor fix 5, logged). Booking refs: `CA-` + 5 chars, insert retried inside a savepoint on 23505 for `bookings_ref_unique` (5 attempts).

### Guest screens and B6 step 1
- **What:** shared `src/lib/occupancy.ts` (`fitsRoom`). G2 and G3 price the whole party as up to 4 rooms of one type (`roomsNeeded`, `splitParty`, `offerFor` in `(guest)/_lib/cart.ts`), never more rooms than are free; more than 4 is a group enquiry; short stock fills the free rooms and says "add another room type on the next step". Reserve carries `/book?checkIn&checkOut&adults&children&room=<type>.<plan>.<adults>.<children>` (repeated, in cart order, max 4). `/book` edits the cart: type and plan per line, adults and children per line, add or remove (1 to 4), a guests-left counter from the original search, per-line errors (occupancy, stock, server `lineIndex`), live quote per line and total. Continue goes to the `/book/details` placeholder.

## S2 booking flow (Claude Code, 2026-11-08, branch `claude/booking-flow`)

### Steps 2 and 3, payment and confirmation (B6 to B9)
- **Flow:** `/rooms` (optional promo, `promo` URL param) → `/book/details` (server re-quote with the `/rooms` parser; inline sign up reusing `guestSignUpAction` with `next` = this URL, or name, email, editable phone and consent on file) → `holdStay` action (Zod, `requireRole('guest')`, double hold guard via `listForGuest`, `acquireBookingHold`) → `/book/pay/[ref]` (HoldTimer, three test outcomes, 2 minute pay gate, Refresh hold) → `payBooking` (amount = saved `total_paise`, `attemptId` rendered by the server, provider id `mock_<bookingId>_<attemptId>`) → `/booking/[ref]` (confirmation, `.ics`, email view).
- **Why the details page re-quotes:** the URL is untrusted. The hold uses the URL `quoteHash`, so a price change since `/rooms` returns `PRICE_CHANGED` (old and new total, "Continue at ₹x" resubmits with the new hash). A change already visible when the page renders is shown before the form.
- **Back to `/rooms`:** `SOLD_OUT`, `BLACKOUT`, line errors and `PROMO_INVALID` redirect with the cart and a display-only `notice` param (`sold-out.<roomTypeId>`, `blackout`, `line.<i>.<code>`); the stay builder shows it as a banner and on the room card or line, until the next edit.
- **Mock gateway:** `MockProvider` signs `{ providerPaymentId, bookingId, amountPaise, status }` with HMAC SHA-256 (`PAYMENT_WEBHOOK_SECRET`) and calls `handleMockWebhook`, the same function `/api/payments/mock` uses, in process. Declined and timeout send no webhook. The pay action then re-reads the booking: CONFIRMED → confirmation; not HELD → refund copy; HELD → "didn't hear back" with Check status and Retry (new attempt id).
- **Pay gate:** under 2 minutes the button is disabled and Refresh hold appears (`cancelHeld`, then a fresh `acquireBookingHold` at the price seen); the action rechecks the gate on the server. Because of it, the late-payment refund copy is not reachable from the UI; it is covered by the pay action unit tests and `tests/integration/staff-read.test.ts`.
- **Three month window (A10):** `src/lib/booking-window.ts`; `validateSearch` gains `too-far`, so home, `/rooms` and room detail share it; `/book/details` and `acquireBookingHold` (`OUTSIDE_WINDOW`) check it again.
- **Confirmation and outbox:** derived from the frozen booking snapshot. `/booking/[ref]/email` (owner) and `/dev/outbox` (staff, last 20 confirmed) render the same email; nothing is sent.
- **A5:** `/admin/bookings` (filters, Refund pending tab) and `/admin/bookings/[ref]` (lines, payments, timeline) through additive `listForStaff`, `getForStaff`, `listRefundPending` (reservations or gm; nav hidden for sales).
- **Known limits:** failed and timed out attempts are not stored; Refresh hold can lose the last unit between cancel and reacquire; zero total stays are not payable online; the mock email is a rendered view. Pages that call `notFound()` inside a streamed Suspense boundary answer HTTP 200 with the 404 screen (the `.ics` route answers a real 404). Against the Neon development branch from this machine a round trip is about 490 ms, so a hold takes 15 to 30 s and a payment up to 30 s in `pnpm dev`; query batching is a follow up.
- **Tests:** unit for the latch, window, cart promo, hold-flow mapping, `holdStay`, pay actions, webhook and `MockProvider`, confirmation, filters; PostgreSQL `cancel.test.ts` and `staff-read.test.ts`; Playwright `e2e/booking.spec.ts` (`pnpm test:e2e` with `E2E_BASE_URL`).
